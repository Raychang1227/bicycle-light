02 / Communication

BLE for the bicycle, Wi-Fi for settings

The micro:bit supplies button and accelerometer information over Bluetooth Low Energy. The ESP32-C6 uses those inputs to run the rear-light state logic. The project uses native micro:bit Button, Accelerometer and Event Services. It does not use a UART service for this communication.

The front and rear units therefore do not need a long signal cable running along the bicycle. The wireless link is part of the prototype’s operating architecture; its range, reconnection performance and behavior under interference still require measurement.

Two wireless roles

  • BLE: transfers rider inputs and motion information between the front and rear units.
  • Local Wi-Fi: lets a phone access the ESP32-C6 settings webpage and experiment functions.

The phone webpage does not require an internet connection or an installed app. This statement refers to the prototype’s local configuration interface, not to the online exhibition website.

The source brief does not specify packet-level formats, service UUID values or a verified connection-loss policy. Those details should be checked against the current firmware before they are described as implemented behavior.

BLE 用於車頭與尾燈通訊，Wi-Fi 用於手機設定。沒有提供的封包細節、斷線處理及連線距離，不自行補上。

03 / Motion processing

Interpreting acceleration

Acceleration contains more than a rider’s intended braking action. Mounting angle, changes in slope and vibration can affect the recorded signal. The project includes several processing steps intended to reduce those influences. Their practical benefit must be established through physical tests.

Start-up calibration

At the beginning of a demonstration, the model should be held in its intended upright posture and kept still for calibration. This establishes a starting reference. It does not teach the program which physical direction means forward travel.

Moving-average filtering

A moving average combines recent samples to make rapid fluctuations less dominant. The filtering settings influence how the program interprets short events. A stronger filter may smooth noise but can also change response timing, so the effect should be measured rather than assumed.

Slow slope-baseline tracking

The program slowly tracks a baseline related to posture or slope. This is intended to reduce the influence of gradual orientation changes on braking decisions. The exact behavior depends on the current parameters and on the way the sensor is mounted.

Correct axis and direction

The sensor axis associated with forward and backward motion, and its positive or negative direction, must be configured correctly. Remembering the starting posture cannot automatically solve this direction problem. Record the mounting and axis settings in each comparison experiment.

From a decision to an output

When the logic identifies a braking event, it starts a red flashing warning and the buzzer. A software record can show that the logic triggered. Direct observation or video is still needed to confirm the physical light output. Light-output verification and detection-rate calculation are related but separate checks.

開機校正只能記住起始姿勢，不能自動辨認車子前進方向。平均濾波與緩慢坡度追蹤都以改善判斷為目標，仍須用實際資料比較。

Turn-side lighting

The four LEDs on the selected side show the amber directional animation. The opposite side maintains its original illumination. The program includes turn-return detection and a timeout for canceling a signal. Fixed cancellation times are not stated here because the current configuration has not been supplied.

Normal illumination

Riding illumination uses soft steady red light with two green center LEDs. Parking illumination uses steady red after a configured stillness period. The software caps brightness. Color choices and a working light pattern do not themselves establish compliance with road-lighting rules.

SOS and standby

SOS uses alternating red and white light and an alarm to attract nearby attention. The three-second continuous A+B hold provides a deliberate clearing action. Standby turns the light output off after prolonged inactivity but does not completely remove power from the system.

05 / Operating modes

Parameters for two contexts

Mode 1: demonstration

This mode is designed for the physical model. Hold the model upright for start-up calibration. More sensitive braking settings make short-distance demonstrations easier. A tilt beyond a configured angle, maintained for the required confirmation duration, can trigger SOS.

Mode 2: riding

This mode uses different braking, impact and tilt parameters. Its goal is to reduce unwanted triggers during ordinary riding movements. That goal is not a measured result, and the mode name does not establish that the prototype has passed road-use certification.

The gold touch logo and the phone webpage can switch modes. Each test run should preserve the chosen mode and its settings. Comparing two modes without controlling other conditions would make it difficult to explain why outcomes differ.

展示模式較適合模型短距離操作；騎乘模式改用另一組參數。請保留每次試驗的模式與設定，才能公平比較。

06 / Phone settings

Configuration without an app

The ESP32-C6 provides an offline Wi-Fi webpage. A phone connects to the prototype’s network and opens the local page. The network name and webpage address must come from the current firmware configuration; this brief does not supply those values.

The supplied phone screen recording shows a live acceleration view: a blue trace for braking-related acceleration changes and a dashed red trigger threshold. This makes the signal and decision boundary visible. The displayed values belong to that recording, rather than a recommended configuration or a measured detection success rate. Watch the phone recording on the main page ↗

Approximately 49 parameters cover sensitivity, confirmation periods, filtering, tilt angle, lighting, sound and standby time. The webpage also offers mode switching and the braking-test schedule. These are the known parameter families, not an invented list of exact field names.

A useful adjustment cycle

  1. Record the current mode, mounting orientation and parameter set.
  2. Choose a repeatable physical action and a defined observation period.
  3. Run the schedule and confirm which actions actually occurred.
  4. Inspect both recorded triggers and the real light output.
  5. Change a small, documented set of parameters and compare under consistent conditions.

This is a proposed way to use the available configuration and recording features. It does not imply that an optimal setting or a validated performance level has already been found.

No software battery-level or fully-charged-state sensing is implemented. The settings webpage cannot report a verified battery percentage or charge-complete state from software measurements.

07 / Experiment design

A braking-test protocol

The implemented scheduler accepts 1–100 rounds, with 30 as its default. Each round contains a preparation period and an observation period. It records whether the logic triggered and saves acceleration data.

Before a run

  • Document the operating mode, firmware version when available and the settings used.
  • Check the mounting, forward sensor axis and positive/negative direction.
  • Complete start-up calibration in the intended starting posture.
  • Define the physical action and keep conditions comparable across parameter sets.
  • Arrange a way to observe the real light output, such as a video recording.

During the scheduled rounds

Use the preparation period to get ready for the action. During observation, perform the intended braking action. Keep the program’s acceleration and trigger records. A scheduled round alone does not prove the action happened.

After a run

Manually confirm the rounds in which braking actually occurred. Exclude rounds in which no braking action occurred, and rounds whose action remains unconfirmed, from the braking-success-rate denominator. Do not silently treat excluded rounds as successful or failed braking trials.

Braking detection success rate

Triggered, manually confirmed braking rounds
÷ all manually confirmed braking rounds
× 100%

When there are zero confirmed braking rounds, the rate is unavailable. The interactive calculator on the main page illustrates this rule with visitor-entered example counts. It does not save those numbers as experimental evidence.

Separate false-trigger testing

A braking-only success rate cannot show how often the device triggers without braking. Plan separate non-braking trials, describe the actions and observation periods, and record unwanted triggers. Include the relevant trial count and conditions when reporting the result.

Physical output and broader performance

Observe the real LEDs rather than relying only on trigger logs. Record whether the expected pattern appears. Battery runtime, daylight and low-light visibility, standby recovery and behavior under different movements require their own documented tests.

排程次數不等於有效煞車次數。只有人工確認確實煞車的輪次能進入分母；分母為零時不計算。誤觸必須安排另外的非煞車試驗。

08 / Records & reporting

Preserving the evidence

The system can export four CSV files: trial-by-trial results, complete acceleration data, the settings used in the run and a success-rate summary. Keeping all four together helps connect a summary result to its actions, signal and configuration.

ExportQuestion it helps answer
Trial-by-trial resultsWhat happened in each scheduled round?
Complete acceleration dataWhat motion signal did the system record?
Run settingsWhich configuration produced those decisions?
Success-rate summaryWhat rate follows from the confirmed braking rounds?

An offline reporting tool can produce trial-outcome plots, acceleration and threshold plots, parameter comparisons and data-quality prompts. It exports PNG, SVG, PDF or HTML containing data.

Before/after figures should identify the parameter sets and test conditions. A visually attractive plot cannot compensate for missing action confirmation, an incorrect denominator or a lack of output observation. No measured project dataset or numerical performance chart has been provided for this showcase, so none is fabricated here.

09 / Status & limits

What is established so far

The physical demonstration model and printed enclosures have been completed. Compilation and computer-side testing have been performed. The known implementation integrates rider inputs, motion sensing, local sound and light, offline adjustment and experiment records.

Formal physical performance measurements remain pending. Outdoor recordings are demonstration evidence, while claims about detection performance require a suitable test. This website does not present the recordings as a substitute for confirmed test results.

  • False triggers remain possible, including from motions that can resemble an intended event.
  • The system cannot be claimed to detect every fall or to guarantee accident prevention.
  • SOS is local. It has no GPS, automatic emergency calling, SMS or remote rescue notification.
  • There is no software battery-level or fully-charged-state sensing.
  • Battery runtime has not been measured. A 400 mAh capacity does not establish a four- or five-hour runtime.
  • Calibration does not automatically determine the bicycle’s forward direction.
  • Trigger logs show a program decision. Actual light output still needs observation.
  • No road-use certification, waterproofing certification or universal crash-detection claim is established by the supplied materials.

Next work

Carry out confirmed braking and separate non-braking trials. Compare parameter sets under consistent conditions. Measure runtime with documented brightness, sound and wireless activity. Verify visibility in different viewing conditions and review the mechanical installation. These are proposed validation tasks rather than completed achievements.

10 / Judges’ questions

Clear answers, including the limits

What is your main design contribution?

The integration of rider-operated signals, automatic motion warnings, local light-and-sound feedback, phone adjustment and inspectable test records in one working prototype. Individual functions may already exist elsewhere. A prior-art review is required before claiming patent novelty.

Why combine manual and automatic functions?

A rider can explicitly request a turn signal, while the sensor can support warnings associated with motion. Combining them allows the same rear unit to express different situations. The practical benefit still needs evaluation with suitable users and physical tests.

Where is the sensor, and does it move with the model?

The accelerometer is built into the front micro:bit controller, which is fixed to the model. It moves and tilts together with the model, allowing a visible demonstration of input and response.

Why use two wireless units?

The front unit provides accessible rider controls and sensor data, while the rear unit provides the visible output. BLE links them without a long signal cable along the bicycle. Range and reliability still require measurement.

Does the project use Bluetooth UART?

No. The specified communication uses the native micro:bit Button, Accelerometer and Event Services rather than UART.

How do you reduce braking false triggers?

The program includes start-up calibration, moving-average filtering and slow slope-baseline tracking, together with adjustable parameters. These are design measures intended to reduce unwanted triggers. Their effectiveness has not yet been established with supplied formal measurements.

Does calibration automatically identify forward travel?

No. It records the starting posture. The correct forward sensor axis and its positive/negative direction still need to be configured.

What is the difference between the modes?

Demonstration mode is more sensitive for short model movements and permits a sustained-tilt SOS demonstration. Riding mode uses different braking, impact and tilt parameters, with the goal of reducing unwanted triggers during ordinary use. The goal remains to be validated.

What is the measured detection success rate?

No formal value has been supplied. The project includes a test scheduler and records, but those features are not themselves a result. Only manually confirmed braking rounds should enter the braking detection-rate denominator.

Can excluded rounds tell you the false-trigger rate?

Not by themselves. Exclusion means they do not belong in the braking denominator. False-trigger evaluation needs separately identified non-braking actions, documented conditions and an appropriate trial count or observation period.

Does an SOS alert send a rescue message?

No. It uses local red/white light and an alarm to attract nearby attention. There is no GPS location, automatic call, SMS or remote rescue notification.

How is SOS cleared?

Hold A and B together continuously for three seconds. A short A+B press is the hazard-light control, which is a different operation.

How long does the battery last?

Runtime has not been measured. Record brightness, sound activity, wireless use and the standby pattern before reporting a duration.

Can the phone show the battery percentage or a full charge?

No software battery-level or charge-complete sensing is implemented. The local settings page does not provide a verified software measurement of either state.

Is standby the same as switching everything off?

No. It turns the LEDs off after prolonged inactivity. Detected movement restores the lighting. It is not a complete power shutdown of the whole system.

Is the prototype certified for road use?

No such certification has been established in the supplied materials. The riding-mode name describes a parameter set, not a certification. Additional testing and assessment are needed.

What would you test next?

Confirmed braking detection, separate non-braking false triggers, actual output behavior, battery runtime, visibility and the mechanical installation. Keep the configuration and conditions with each run so that results can be interpreted.

答辯重點：說明整合設計及驗證方法，沒有數據就直接回答待測，不把展示影片當成功率，也不把 SOS 說成遠端救援。
